# Review Outstanding Changes

Review the code the user hasn't shipped yet — and only that code — the way a senior teammate who knows this codebase well would. The goal is not a generic lint pass: it's catching the things a reviewer familiar with *this* project would catch: "we already have a helper for that", "every other handler does it this way", "the UI layer shouldn't be talking to the DB", "this function does three jobs".

The output is a prioritized report. Then offer to fix. Never modify code before the user picks what to apply.

## Step 1 — Collect the outstanding changes

"Outstanding" means everything not yet on the remote: staged, unstaged, untracked, plus local commits not pushed.

```bash
git rev-parse --show-toplevel            # confirm we're in a repo
git status --porcelain=v1
git diff HEAD                            # staged + unstaged vs last commit
git ls-files --others --exclude-standard # untracked files — read these in full
```

Unpushed commits — find the base, in order:
1. If the user passed a ref (`/review-outstanding main`, `HEAD~3`, a SHA), use it as the base.
2. Else the upstream: `git rev-parse --abbrev-ref @{u}` → base is `@{u}`.
3. Else the default branch's merge-base: try `origin/HEAD`, then `origin/main`, `main`, `origin/master`, `master` → `git merge-base <that> HEAD`.
4. Else (brand-new repo, no remote) only the working tree counts.

Then `git log --oneline <base>..HEAD` and `git diff <base>` (diffing the base against the *working tree* folds commits and uncommitted work into one view). If the user passed file paths instead of a ref, restrict to those paths.

Keep track of *where* each change lives (unpushed commit / staged / unstaged / untracked). Which state a change is in matters on its own: if the commits about to be pushed hold half a feature while the other half is untracked, or a new file is imported by committed code but never `git add`ed, that's worth stating at the top of the report. It's an easy way to ship something broken.

If there's nothing outstanding, say so and stop — don't review the whole repo. Skip generated/vendored noise (lockfiles, `dist/`, snapshots, migrations generated by tools) unless the user asks; mention that you skipped them.

Note the size. Under ~400 changed lines: do the review yourself. Larger, and if you can spawn subagents: split by axis group (Step 3) so each reviewer gets a clean context.

## Step 2 — Learn the codebase before judging it

A diff reviewed in isolation produces generic advice. The value of this skill comes from comparing the change to the code around it, so spend real effort here.

**Standards sources.** Read whatever documents how code should be written: `CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md`, `CODING_STANDARDS.md`, `docs/` style guides, `.cursor/rules`, `.github/copilot-instructions.md`. Glance at lint/format config (`eslint`, `ruff`, `prettier`, `.editorconfig`, `tsconfig` strictness) only to learn what tooling already enforces — don't report those things; the tooling will.

**Spec sources** (what was the change *supposed* to do), in order: issue refs in commit messages or the branch name (`#123`, `PROJ-45`) — fetch via `gh issue view` or an available tracker tool if possible; a path the user passed; a spec/plan in `docs/`, `specs/`, `plans/`, `.scratch/` matching the branch/feature; the current conversation if the user described the task. If none exists, don't stall — skip the spec axis and say "no spec found".

**Architecture.** Map the layout: top-level dirs, layer boundaries (e.g. `routes → services → repositories`, `ui → hooks → api`, `domain` with no framework imports), module boundaries, ADRs in `docs/adr` or `docs/architecture`. Check how imports flow in a few existing files — the de-facto architecture is what the code does, even if it's undocumented.

**Pattern neighbors.** For each changed file, open 2–3 existing *siblings of the same kind* (another route, another component, another repository, another test) and note their conventions: error handling, naming, file structure, how they validate input, log, fetch data, handle config, write tests.

**Existing helpers.** For each new function/component/constant in the diff, search (`grep`/`rg`) for something that already does the same job — similar names, the same regex, the same API call, the same formatting. Check `utils/`, `lib/`, `shared/`, `common/`, `helpers/`, `hooks/`. Reinventing an existing helper is one of the most valuable things to catch, and one of the easiest to miss without looking.

## Step 3 — Review across six axes

Each axis is its own lens. A change can pass one and fail another — don't let a clean result on one mask problems on another.

**Group A — Correctness of intent**
1. **Standards** — violations of the repo's *documented* rules (cite the doc + rule). Only documented rules can be hard violations.
2. **Spec** — requirements missing or partial; behavior the spec didn't ask for (scope creep); things that look implemented but wrong. Quote the spec line.

**Group B — Fit with the codebase**
3. **Pattern consistency** — does the change do something differently from how the codebase already does it? Different error-handling style, a new HTTP client when one exists, a different state-management approach, naming that breaks convention, a test structured unlike its neighbors. Every finding must cite the existing pattern (`path:line`) it diverges from. A divergence that's a deliberate improvement isn't automatically wrong — say so, and suggest either aligning or noting it as a new convention.
4. **Architecture** — does the change break the project's structure? Layer skipping (controller calling the DB directly), dependency direction reversed (domain importing from UI/framework), cross-module reach into internals, business logic in the wrong layer, new circular imports, a new top-level concept that doesn't fit the existing layout. Cite the boundary and the evidence that it's a boundary.

**Group C — Design quality**
5. **Refactoring opportunities** — clean code, KISS, single responsibility. Functions doing several jobs, deep nesting, long parameter lists, boolean flag params, unclear names, needless cleverness, dead code, over-engineering. Use the smell baseline in the Appendix below as judgement-call heuristics.
6. **Reuse & extraction** — (a) code that duplicates an *existing* helper → use it (cite it); (b) logic repeated within the diff, or repeated between the diff and existing code → extract. Apply the rule of three loosely: two near-identical copies is worth flagging, a single use is not a reason to extract. Recommending a premature abstraction is itself a smell (Speculative Generality).

With subagents: spawn three in parallel (A, B, C). Give each the base ref + exact diff command, the list of changed/untracked files, and what you learned in Step 2 that its axes need (standards docs and spec for A; architecture map, pattern neighbors for B; helper search results and the Appendix (smell baseline + extraction checklist) for C — subagents can't see your context, so paste it in). Ask each for findings in the format below, under ~500 words. Without subagents, work through the groups yourself in order.

### Ground rules for findings

- **Review the change, not the repo.** Only flag pre-existing problems if the change makes them worse or extends them; label those "pre-existing".
- **The repo overrides the baseline.** If the codebase consistently does something a textbook would call a smell, consistency wins — don't flag it.
- **Skip what tooling enforces** (formatting, import order, lint rules that are configured).
- **Evidence or it didn't happen.** Every finding names `file:line` in the change, and for pattern/architecture/reuse findings, the existing code it's compared against. If you can't point to evidence, drop it or phrase it as a question.
- **Heuristics are labeled as such** ("possible Feature Envy"), not stated as violations.
- **Don't pad.** Five real findings beat twenty nitpicks. If an axis is clean, say "No issues" — that's useful information.

### Severity

- **Blocker** — wrong behavior vs spec, breaks a documented rule or a real architectural boundary, or will clearly cause bugs.
- **Should fix** — clear pattern break, duplicates an existing helper, obvious SRP/KISS problem a reviewer would push back on.
- **Consider** — judgement calls, optional polish.

## Step 4 — Report

Use this structure:

```markdown
# Outstanding changes review

**Scope:** <N files, +X/−Y lines> — <uncommitted | K unpushed commits since <base>> (skipped: <generated files, if any>)
**Context used:** <standards docs read> · spec: <source or "none found"> · compared against: <key neighbor files>
**Change state:** <only if it matters, e.g. "the unpushed commit holds the repository only; routes/invoices.js is untracked, so pushing now ships half the feature">.

## Fix first
1. [AR1] <one line> — <file:line>
2. ...   (up to 5, the highest-value items across all axes)

## Standards
## Spec
## Pattern consistency
## Architecture
## Refactoring (clean code · KISS · SRP)
## Reuse & extraction

(Each section: findings, or "No issues.")

### [ID] <short title> — <Blocker | Should fix | Consider>
- **Where:** `path:line`
- **Why:** what's wrong, with the evidence (existing pattern/helper/boundary at `path:line`, or the spec/doc quote)
- **Fix:** concrete suggestion — a few lines of code where it helps

**Summary:** <counts per severity>. <one sentence on the overall shape of the change>.
```

IDs are an axis prefix + number so the user can pick them later: `ST` standards, `SP` spec, `PC` pattern consistency, `AR` architecture, `RF` refactoring, `RU` reuse (e.g. `PC1`, `RU2`). Use the same IDs in "Fix first".

## Step 5 — Offer fixes

After the report, ask which findings to apply. Offer sensible groupings: "all Blockers + Should fix", specific IDs, or "none". Use a multiple-choice question tool if one is available; otherwise ask in text.

When applying:
- Change how code works, never what it does (unless fixing a spec/correctness finding — then say so).
- Keep edits minimal and in the existing style; when reusing a helper or extracting one, put it where the codebase keeps such things.
- Run the project's tests / typecheck / lint afterwards if they exist and are quick, and report the result.
- Don't commit, stage or push — the user decides that.
- Finish with a short list of what changed, per ID, and anything you skipped and why.

## Appendix — Smell & principle baseline

Heuristics for the Refactoring and Reuse axes. Every one is a **judgement call**: label findings as "possible X", and drop them when the repo consistently does otherwise (the repo overrides the baseline) or when tooling already enforces the rule.

### Fowler smells (Refactoring, ch. 3) — symptom → usual fix

| Smell | Symptom | Fix |
|---|---|---|
| Mysterious Name | You can't tell what it does from its name | Rename. If no honest name comes to mind, the design is murky — say that. |
| Duplicated Code | Same shape in 2+ places (in the diff, or diff vs existing code) | Extract the shared shape, or call the existing one |
| Long Function | Has to be scrolled; sections separated by comments | Extract functions named after what the comments say |
| Long Parameter List | 4+ params, or params always passed together | Parameter object, or pass the thing the params came from |
| Feature Envy | Method mostly reads another object's data | Move it onto the data it envies |
| Data Clumps | Same 3+ fields travel together | Bundle into one type |
| Primitive Obsession | Strings/numbers standing in for a domain concept (ids, money, status codes) | Give the concept a small type or enum |
| Repeated Switches | Same switch/if-chain on the same discriminator in several places | One map or polymorphism shared by all sites |
| Shotgun Surgery | One logical change forces edits across many files | Gather what changes together into one module |
| Divergent Change | One module changes for unrelated reasons | Split so each changes for one reason |
| Speculative Generality | Hooks, params, abstractions, or config with one (or zero) users | Inline/delete until a real second need appears |
| Message Chains | `a.b().c().d()` | Hide the walk behind one method |
| Middle Man | A class/function that only delegates | Call the target directly |
| Refused Bequest | Subclass ignores/overrides most of what it inherits | Composition instead of inheritance |
| Flag Argument | Boolean param that switches behavior | Two functions, or an explicit enum |
| Dead Code | Unused vars, unreachable branches, commented-out code | Delete it |

### Principles

**KISS.** Prefer the most direct code that solves the actual problem. Flags: clever one-liners that need a comment to decode, nested ternaries, generic frameworks built for one caller, reflection/metaprogramming where a plain call works, configuration for things that never vary. The fix is usually *less* code.

**Single Responsibility.** A function, component, or module should have one reason to change. Flags: a function that fetches, transforms, and renders; a component that owns data loading, business rules, and layout; a name with "And" in it (or that would need one to be honest); a file whose imports span unrelated domains. The fix is to split along the seams, matching how the codebase already splits things (e.g. if the repo puts data loading in hooks, the split goes there).

**Clean code.** Intention-revealing names; small functions at one level of abstraction; early returns over deep nesting; no magic numbers/strings where the repo has constants; comments explain *why*, not *what*; errors handled the way neighbors handle them.

**DRY — with restraint.** Duplication of *knowledge* (a business rule, a regex, an endpoint URL, a validation) is worth removing even at two copies. Duplication of incidental *shape* (two loops that happen to look alike) usually isn't until the third copy. Wrong abstractions cost more than duplication — when unsure, say "consider" rather than "should fix".

### Extraction checklist (Reuse axis)

Before recommending an extraction, confirm:
1. Does something in the codebase already do this? Search `utils/`, `lib/`, `shared/`, `common/`, `helpers/`, `hooks/`, and grep for distinctive literals (regexes, URLs, error messages, key names). If yes → "use existing `path:symbol`", which beats creating anything new.
2. Are there ≥2 real call sites (in the diff or diff + existing)? One call site → don't extract.
3. Do the copies represent the same *concept* (will they change together)? If they'll diverge, leave them.
4. Where would it live? Name the directory based on where the repo keeps similar helpers.
